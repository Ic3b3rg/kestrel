# Memoria e orchestrazione di una run Kestrel

**Ricerca del 2026-10-01.** Domanda: come distribuire inferenza, agente, comandi di sviluppo, servizi/test e review PR per eseguire un task end-to-end anche su una macchina Kestrel da 16 GiB, senza scambiare limiti configurati per una verifica riuscita? Qui **documentato/osservato** indica una fonte o misura esistente; **proposta** indica una scelta ancora da provare. La [ricerca sui backend di esecuzione](./factory-runner-capabilities-assessment.md) confronta host, Docker, VM e cloud; questa nota riguarda l'ammissione e il ciclo di vita del *lavoro* su quei backend.

## Fatti rilevanti

- **Osservato in Kestrel.** Il checkout runtime locale separa Codex App Server sull'host, `exec-server` in container, e container nuovi per la verifica. Il default dell'`exec-server` è 2 GiB, 2 CPU e 128 PID; abilita `multi_agent`/`multi_agent_v2` con massimo 3 thread concorrenti per sessione ([runtime corrente](/Users/silvioceccarini/Projects/kestrel-runtime/apps/web/src/codex-execution-runtime.ts:127), [contratto](./factory-execution-runtime-contract.md)). È un *massimo di thread*, non tre budget indipendenti né prova che ogni thread abbia 2 GiB: i loro comandi condividono il limite della run. La documentazione di `origin/master` è meno recente del checkout runtime, quindi questi numeri descrivono solo la run locale corrente.
- **Osservato nelle run conservate.** Il database locale registra per le tre run più recenti esiti `timeout`, `usage_limit` e `unavailable` e centinaia di eventi di comando; non registra campioni RSS, `memory.peak` né un picco del modello/VM. La review Kestrel corrente legge la revisione base/head in sola lettura e i risultati dei check già eseguiti; le sue istruzioni vietano di eseguire il codice del progetto ([runtime review](/Users/silvioceccarini/Projects/kestrel-runtime/apps/web/src/codex-review-runtime.ts:8), [processore](/Users/silvioceccarini/Projects/kestrel-runtime/apps/web/src/conceptual-review-processor.ts:147)). Una review completata non sostituisce quindi una prova eseguita.
- **Osservato sul repository GitHub.** Il checkout `kestrel` non contiene `.github/workflows`; il comando `gh pr checks 306 --repo Ic3b3rg/kestrel` ha restituito `no checks reported` e l'API GitHub non riporta review sulla PR aperta #306 al 2026-10-01. Questa è una fotografia di quella PR, non una regola universale del repository: non attribuire a un bot o a CI verifiche che non risultano nei check GitHub.
- **Osservato sulla macchina.** Host 24 GiB (`sysctl hw.memsize`: 25.769.803.776 byte), VM Docker Desktop circa 7,75 GiB (`docker info`: 8.319.238.144 byte), `exec-server` 2 GiB. La misura di #142 qui sotto distingue questi limiti dall'uso effettivo. Docker Desktop configura una VM con memoria propria; Docker Engine può imporre cap hard/soft ai singoli container ([Docker Desktop](https://docs.docker.com/desktop/settings-and-maintenance/settings/), [Docker Engine](https://docs.docker.com/engine/containers/resource_constraints/)). Una macchina da 16 GiB richiede misure proprie prima di dichiarare supporto.
- **Documentato altrove.** Warp separa definizione di ambiente, shape del runner (OS/architettura/vCPU/memoria) e sede dell'esecuzione; supporta compute hosted e worker self-hosted Docker, Kubernetes o Direct sull'host ([Warp](https://docs.warp.dev/factories/infrastructure-and-security/)). Fabro distingue configurazione di ambiente e sandbox istanziata, con provider locale, Docker e Daytona; Docker permette override di CPU/memoria per run ([Fabro](https://github.com/fabro-sh/fabro/blob/main/docs/public/execution/environments.mdx), [sandboxing](https://github.com/fabro-sh/fabro/blob/main/docs/public/administration/sandboxing.mdx)). Cloudflare Containers offre shape da 256 MiB a 12 GiB e quote aggregate di account: anche il cloud ha limiti espliciti ([Cloudflare](https://developers.cloudflare.com/containers/platform/limits/)). Nessuno di questi fatti dimostra che una forma sia adatta a #142 senza misurarla.
- **Documentato per l'inferenza.** Docker Sandboxes consente modello sul computer host, provider hosted o endpoint compatibile configurato (anche GPU server interno); quando il modello è host, memoria/compute restano fuori dal budget della sandbox ([modelli Docker](https://docs.docker.com/ai/sandboxes/configuration/models/)). Un proxy host-side può mantenere le credenziali fuori dalla sandbox e iniettare solo gli header autorizzati ([credenziali Docker](https://docs.docker.com/ai/sandboxes/configuration/credentials/)). Ollama, come esempio di server locale, espone di default `127.0.0.1:11434`, può disabilitare il cloud, e documenta che parallelismo e lunghezza contesto aumentano la RAM; `keep_alive` controlla la permanenza del modello caricato ([FAQ Ollama](https://docs.ollama.com/faq)). Questi pattern non provano che il Codex App Server Kestrel supporti già un endpoint privato specifico: occorre verificare adattatore, autenticazione, tool calling e modello scelto.
- **Documentato per la pressione.** Su Linux cgroup v2 `memory.high` rallenta/reclama senza OOM, `memory.max` è un limite hard; `memory.events` e `memory.pressure` permettono di osservare il problema. Un cap hard da solo produce terminazioni, non admission control ([kernel Linux](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)).

## Prova misurata su #142 (2026-10-01)

La prima prova campionata, run `01a0f8fb-8b1a-7bf2-b4ed-9e39269d4642`, è una ripresa del checkpoint esistente, non una nuova implementazione da zero. Il campionatore ha registrato 57 campioni fra 19:38:44 e 19:44:54 UTC, includendo baseline, run e cleanup. Il container di implementazione ha raggiunto esattamente il cap di **2.048 MiB** (`memory.peak`); `memory.events.max` è arrivato a **646**, mentre `oom` e `oom_kill` sono rimasti **0**. Il gruppo di processi del servizio Kestrel sull'host ha raggiunto **1.305 MiB RSS** (circa 819 MiB prima dell'avvio), Docker backend **255 MiB RSS**, e il minimo osservato di memoria libera secondo `memory_pressure -Q` è stato **43%**. Queste RSS non sono addendi indipendenti del totale fisico: pagine condivise e la memoria della VM complicano la somma. Il modello usato era `gpt-6.1-sol` via sottoscrizione Codex, con inferenza fuori dal container; nessun modello locale era caricato per questa prova. La run si è fermata prima della verifica perché l'agente ha chiamato `clock.sleep`, uno strumento host che il controller ha negato. La traccia Codex conservata identifica la chiamata; il blocco `permission_required` non era una richiesta di scelta di prodotto.

La seconda ripresa, run `01a0f904-c041-7bf5-99d5-43b50fa1ce3a`, ha superato l'implementazione ed è entrata nei nove check approvati. È durata **1.912 secondi (31:52)** ed è terminata con `verification_failed`, non con timeout: al secondo 1.814 era ancora in `verifying` con heartbeat aggiornato. Il campionatore ha registrato 288 campioni fra 19:50:15 e 20:22:33 UTC e ha osservato 22 container del task; i più brevi possono essere sfuggiti all'intervallo di circa 5–7 secondi. Il container agente ha raggiunto **1.359 MiB** di `memory.peak`, senza OOM; la sua cgroup PID ha toccato **128/128** con **13** eventi `pids.events.max`. Il container del check `lint` ha raggiunto circa **1.310 MiB**; Node è uscito con codice **134** dopo aver esaurito il proprio heap V8 intorno a 1 GiB, pur restando sotto il cap del container. Il container della suite completa ha toccato anch'esso **128/128 PID**. Il gruppo di processi Kestrel sull'host ha raggiunto **1.453 MiB RSS** e il minimo osservato di memoria host libera è stato **41%**; la misura non include il consumo interno della VM Docker come un singolo RSS sommabile. In tutti i container campionati `oom` e `oom_kill` sono rimasti a zero.

Il controller ha eseguito tre giri tecnici; **in ciascuno quattro check sono passati e cinque falliti**. I check 1–3 richiedono `LOCAL_GIT_EXECUTABLE` e Docker CLI in un percorso macOS (`/Applications/Docker.app/...`) assenti nel runner Linux; il check 6 è `lint` con heap esaurito; il check 8 è la suite completa, con 250 failure nel primo giro. `typecheck`, `contracts:check`, `format:check` e `build` sono passati. La ripetizione dei giri non ha risolto i prerequisiti del runner e ha consumato circa mezz'ora di compute e modello senza produrre una certificazione. Non esiste PR o merge per #142 da questa run.

I file grezzi, esterni ai worktree, sono `~/Library/Application Support/Kestrel/development/measurements/issue-142-20261001.jsonl` e `issue-142-retry2-20261001.jsonl`. I campioni rilevano RSS host, pressione memoria host, `docker stats` e `memory.current/peak/max/events` del container. Il picco PID e i relativi eventi della seconda run sono stati letti direttamente dalla cgroup durante l'esecuzione; il campionatore è stato esteso per conservarli nelle prossime prove. Mancano ancora una misura GPU/VRAM, consumo energetico e un confronto su macchina da 16 GiB. I dati dimostrano tre vincoli separati: **quota container**, **limite del singolo processo Node/parallelismo PID**, **capacità del runner per tool e OS**. Aumentare una sola quota non risolve gli altri due.

**Decisione proposta per la prossima iterazione.** Prima dell'ammissione, il controller dovrebbe verificare che ogni comando approvato abbia un runner con OS, eseguibili, accesso ai servizi e budget CPU/RAM/PID dichiarati. Se mancano Docker o un path host richiesto, fermare il piano con `runner_capability_missing` e dettagli concreti, senza spendere tre giri di riparazione e senza chiedere una falsa decisione di prodotto. Per progetti senza servizi basta un runner leggero; per Compose o browser serve una fase di verifica separata, con daemon e risorse posseduti dalla run, senza consegnare il socket Docker generale all'agente. Il budget iniziale deve usare RAM host *e* cap effettivo della VM Docker, lasciare una riserva all'OS/modello locale, quindi regolare concorrenza e memoria per classe di comando. Per Vitest `maxWorkers` o `fileParallelism` riducono i processi ([documentazione Vitest](https://vitest.dev/guide/parallelism.html)); per Node un heap maggiore può evitare exit 134 ma consuma una parte maggiore del cap ([documentazione Node](https://nodejs.org/download/release/v22.17.0/docs/api/cli.html)). Questi knob devono essere un profilo esplicito di verifica e misurati sulla revisione reale, non modifiche silenziose ai check approvati. Un cap Docker dinamico senza preflight, riduzione della concorrenza o capacità dei servizi non certifica #142.

## Proposta: cinque lavori separati, un solo contratto di run

| Lavoro | Sede/autorità proposta | Risorsa da prenotare e prova da conservare |
| --- | --- | --- |
| Inferenza | Servizio sull'host Kestrel **oppure** endpoint privato su altro PC/home lab/azienda; credenziale nel supervisor, accesso limitato alla sola API necessaria. | Su host: RAM *e* memoria GPU/unificata del modello, contesti paralleli; remoto: capacità/latency/quota endpoint e una coda. Non attribuire automaticamente la RAM remota al computer Kestrel. |
| Agente e workspace | Una `AgentRun` con checkout e sandbox posseduti da Kestrel; App Server/credenziali fuori dal processo che esegue il codice del repository. | Un'identità di run, revisione Git, limiti CPU/RAM/PID/disk e heartbeat. I 3 subagent sono concorrenza *dentro* questa prenotazione; ridurli o serializzarli quando build/servizi ne occupano il budget. |
| Build e tool | Processi figli della run, avviati nel backend scelto per il progetto; ogni comando registra PID/identità, exit code, durata e picco. | Slot di CPU/RAM temporanei; `npm install`, compilatore, Flutter/Gradle e browser non vanno dimensionati col solo `exec-server`. Un comando terminato non implica che servizi figli siano terminati. |
| Servizi e test | Container/DB/browser o emulatori con identità e ownership della run; solo backend che dichiara le capacità richieste (Compose, OS, device, display). | Prenotazione aggregata nella VM Docker/host e artefatti di test associati alla revisione esatta. Servizi persistenti contano finché realmente fermati. |
| Review PR | Processo/turno separato dopo checkpoint della revisione; può usare lo stesso modello locale in un secondo momento o modello remoto. CI/test eseguibili restano una prova distinta. | `head SHA` o test-merge SHA, commenti e check ID. La review AI identifica rischi ma non certifica che build/test siano passati: GitHub dice di eseguire test e analisi statica prima, e i required checks devono passare sull'ultimo SHA ([guida GitHub](https://docs.github.com/en/copilot/tutorials/review-ai-generated-code), [status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)). Una nuova push richiede una nuova prova: persino Copilot non ri-esamina nuovi commit senza configurazione esplicita ([Copilot review](https://docs.github.com/en/copilot/concepts/agents/code-review)). |

**Proposta di scheduling.** Il controller ammette una run solo se l'intero *profilo di picco previsto* entra nei due budget separati: `(controller + modello locale residente + run host + riserva OS) ≤ RAM host` e `(exec-server + build/servizi containerizzati + overhead VM) ≤ RAM VM Docker`. Con inferenza remota, la prima disuguaglianza perde il peso del modello ma conserva il traffico/client. Le somme sono prenotazioni conservative, non somma di RSS misurati (pagine condivise e cache rendono quest'ultima fuorviante). Dentro la run, slot per `agent/command`, `build`, `services/test` e `review`; massimo 3 subagent diventa un tetto subordinato agli slot disponibili, non un motivo per avviare tre build insieme. Una build pesante può richiedere di fermare servizi inattivi o attendere un'altra run; scaricare e ricaricare il modello locale ad ogni comando rischia latenza e thrashing, quindi l'eventuale unload va deciso a un confine sicuro tra turni e misurato. Ollama rende configurabili modelli caricati, richieste parallele e `keep_alive`, ma questo non controlla gli altri processi ([FAQ Ollama](https://docs.ollama.com/faq)).

La coda dei task è preferibilmente **FIFO con classi di risorse**, non LIFO: invertire l'ordine non riduce la memoria e può lasciare senza esecuzione i task vecchi. Il guadagno deriva dalla *barriera fra fasi* e dalla prenotazione delle risorse prima di partire. GitHub Actions documenta sia il controllo della concorrenza sia una coda FIFO ([concurrency](https://docs.github.com/en/actions/concepts/workflows-and-actions/concurrency)). Se una singola build richiede più RAM del limite disponibile, serializzarla non basta: serve cambiare shape o sede della build. Per scaricare solo la verifica pesante, si può eseguire CI su runner GitHub mentre l'inferenza resta privata; il workflow `pull_request` verifica per default il merge commit e i required checks devono riferirsi all'ultimo SHA ([evento PR](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [check](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)). Questa opzione richiede adattare la sequenza Kestrel, che oggi apre la PR dopo la verifica, e non offre all'agente Docker durante la sua fase di implementazione.

**Proposta di lifecycle.** Nessun timeout assoluto di 30 minuti per una run sana: deadline del singolo comando, heartbeat del worker, progressi della run e un timeout di stallo sono condizioni diverse. Persistire intent, identità del workspace/container, revisione e ultimo checkpoint; dopo crash, riconciliare processi e servizi posseduti prima di riprendere. L'[ADR 0005](../adr/0005-own-sandbox-custody-with-the-agent-run.md) richiede identità e prova dello stop prima del checkpoint. Cloudflare documenta un caso insidioso: attività dentro il container non mantiene da sola attivo il suo Durable Object; un build o task agente può essere fermato per inattività senza monitor/keepalive, e snapshot conserva file ma non processi ([lifetime Cloudflare](https://developers.cloudflare.com/sandbox/concepts/lifetime/)). La lezione trasferibile è registrare *lavoro vivo* e checkpoint durevole separatamente, non assumere che il processo o il file bastino.

## Misura end-to-end necessaria prima di fissare shape e parallelismo

**Proposta di esperimento ripetibile:** su un checkout esatto di una issue piccola ma reale, annotare `run ID`, commit base/finale, hardware/OS, backend, Docker VM cap, modello e sede (locale/remota), dimensione contesto, numero thread, toolchain e comandi. Campionare ogni 1–5 s da prima dell'avvio a cleanup concluso: pressione/available memory host, RSS dei processi controller/App Server/modello/build, GPU/unified memory se applicabile, `docker stats` e `memory.current/events/pressure` per container e servizi, CPU, PID, disk e durata. Eseguire l'intero percorso: agente → install/build → servizi → test → checkpoint → review → cleanup; conservare log dei comandi, exit code, artefatti, SHA e picchi per fase. Ripetere con 1 e 3 subagent e con inferenza locale e remota; poi due run contemporanee. Una variante con macchina da 16 GiB o limite VM corrispondente è necessaria prima di dichiarare supporto ai 16 GiB. Un successo richiede esito test sulla revisione esatta, nessun OOM/stallo, teardown provato e memoria tornata al baseline ragionevole; se una fase non parte per capacità, registrarla come `capacity blocked`, non come difetto del codice.

**Questioni ancora aperte da misurare:** picco di una verifica realmente compatibile con Docker/Compose, memoria residua di un modello locale dopo idle, costo del cambio modello locale/remoto, sovrapposizione massima fra tre subagent e build, dimensione Docker Desktop necessaria per Compose del progetto, comportamento di ripresa dopo crash durante un servizio, e prova su una macchina da 16 GiB. I picchi misurati di #142 descrivono solo la configurazione attuale e un task non certificato. Questi dati aggiuntivi decidono se basta admission su Direct locale, se serve VM privata con più memoria, o se il lavoro pesante deve andare su compute remoto; la scelta del backend rimane esplicita per fiducia e capacità, come discusso nella [nota precedente](./factory-runner-capabilities-assessment.md).
