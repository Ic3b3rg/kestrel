# Fabro: provider del modello e ambiente di esecuzione sono due scelte diverse

**Data:** 2026-10-02. **Fonti:** repository Fabro `bfe5b33b6a858e31b3451ba3136984abe96a0a4d`, sandbox-driver `7d1932b5fd758dbc67ae5a34aaed08d8733ddaba`, Kody `b9d365435ad92094adde681d691b7a4ecd036194`. Questa è un'ispezione di documentazione e codice, non un benchmark Fabro.

## Risposta breve per Kestrel #142

Fabro **non risolve la necessità di Docker nei test collegando un provider LLM o un MCP**. Separa la scelta del *modello* (API, proxy OpenAI-compatible, Ollama locale, ACP) dalla scelta dell'*ambiente di esecuzione* (`local`, `docker`, `daytona`, o sandbox-driver plugin). Il suo default installato è un container Docker da **2 CPU e 4 GB**, mentre Kestrel #142 era in un container da 2 GB/128 PID. Configurare un ambiente Docker con più memoria può risolvere il check lint di #142 solo se il consumo effettivo rientra; **non rende disponibile `docker compose` all'interno del container dell'agente**, né converte percorsi macOS in Linux. La verifica dei check Docker richiede una capacità distinta: host fidato, daemon Docker dedicato, oppure VM/sandbox con Docker interno. [Fabro sandboxing](https://github.com/fabro-sh/fabro/blob/bfe5b33b6a858e31b3451ba3136984abe96a0a4d/docs/public/administration/sandboxing.mdx), [ambiente predefinito e mapping risorse](https://github.com/fabro-sh/fabro/blob/bfe5b33b6a858e31b3451ba3136984abe96a0a4d/docs/public/execution/environments.mdx#L335-L407), [piano di creazione Docker](https://github.com/lithoscomputer/sandbox-driver/blob/7d1932b5fd758dbc67ae5a34aaed08d8733ddaba/crates/sandbox-driver-docker/src/create.rs#L134-L171).

## Come funziona Fabro, verificato nelle fonti

1. Il backend API di Fabro gestisce il ciclo LLM e manda le chiamate ai tool nella sandbox. Il backend ACP avvia invece un processo agente dentro la sandbox attiva; quel processo possiede credenziali e selezione del modello. Fabro documenta ACP con `local` e `docker`, non con Daytona. Sono due backend dell'agente, non soluzioni alla capacità Docker dei check. [Agent loop e backend](https://github.com/fabro-sh/fabro/blob/bfe5b33b6a858e31b3451ba3136984abe96a0a4d/docs/public/core-concepts/agents.mdx#L198-L265).
2. Gli ambienti hanno provider, immagine e risorse configurabili; `local` esegue senza isolamento, `docker` crea un container, `daytona` una sandbox cloud. Il mapping ufficiale usa i limiti di memoria e CPU del container Docker. Il provider Docker è clone-based e richiede un'immagine con Bash. [Environments](https://github.com/fabro-sh/fabro/blob/bfe5b33b6a858e31b3451ba3136984abe96a0a4d/docs/public/execution/environments.mdx#L363-L407).
3. Se il **server Fabro** gira in Docker, il suo Compose monta `/var/run/docker.sock` nel container *server* per permettergli di creare i container sandbox sul daemon dell'host. La documentazione avverte che questo dà al server accesso equivalente a root sull'host ed è adatto solo a deploy fidati single-tenant. Questo **non equivale** a montare il socket nel container *agente*. [Self-host Docker](https://github.com/fabro-sh/fabro/blob/bfe5b33b6a858e31b3451ba3136984abe96a0a4d/docs/public/administration/self-host-docker.mdx).
4. Nel driver Docker usato da Fabro, il piano base crea un volume workspace proprio e nessun bind; `binds` e `privileged` sono opzioni esplicite, mentre i limiti di memoria e CPU vengono passati al daemon. Il test `a_plain_spec_plans_a_workspace_volume_and_a_blank_bash_env` asserisce `host.binds == None`. Non c'è dunque prova che l'installazione standard Fabro renda il daemon host accessibile all'agente. [Dipendenza Fabro dal driver](https://github.com/fabro-sh/fabro/blob/bfe5b33b6a858e31b3451ba3136984abe96a0a4d/Cargo.toml#L89-L105), [driver create](https://github.com/lithoscomputer/sandbox-driver/blob/7d1932b5fd758dbc67ae5a34aaed08d8733ddaba/crates/sandbox-driver-docker/src/create.rs#L134-L171), [test del default](https://github.com/lithoscomputer/sandbox-driver/blob/7d1932b5fd758dbc67ae5a34aaed08d8733ddaba/crates/sandbox-driver-docker/src/create.rs#L435-L454).
5. Fabro supporta provider sandbox come plugin, ma il plugin deve implementare un vero ambiente che esegue shell/filesystem/lifecycle; un plugin MCP aggiunge tool all'agente, non cambia automaticamente CPU, RAM, OS o daemon Docker. Fabro ha anche `fabro doctor` per connessione LLM e raggiungibilità del daemon e `fabro preflight` per configurazione run. Questi sono due controlli separati. [Sandbox providers](https://github.com/fabro-sh/fabro/blob/bfe5b33b6a858e31b3451ba3136984abe96a0a4d/docs/public/administration/sandboxing.mdx), [MCP tools](https://github.com/fabro-sh/fabro/blob/bfe5b33b6a858e31b3451ba3136984abe96a0a4d/docs/public/agents/mcp.mdx), [troubleshooting](https://github.com/fabro-sh/fabro/blob/bfe5b33b6a858e31b3451ba3136984abe96a0a4d/docs/public/administration/troubleshooting.mdx).
6. Fabro permette provider LLM OpenAI-compatible con `base_url` arbitrario e Ollama. Dunque l'inferenza può risiedere in una LAN o sull'host mentre il codice gira altrove, **se quella rete è raggiungibile e autorizzata**. Il provider LLM cambia dove gira l'inferenza, non dove girano test e build. [Models](https://github.com/fabro-sh/fabro/blob/bfe5b33b6a858e31b3451ba3136984abe96a0a4d/docs/public/core-concepts/models.mdx#L254-L367).

## Kody e alternativa concreta

Kody si definisce una piattaforma di assistente personale MCP-first su Cloudflare Workers, non un harness generale per build/test di repository. La sua documentazione indica Durable Objects e Workflows per esecuzione durevole, con modello/provider portato dall'utente. Il suo `execute` è codice in un runtime Worker con budget (la guida cita timeout di esempio di 90 s), quindi non dimostra che possa eseguire per ore `docker compose` o Flutter. [README](https://github.com/kentcdodds/kody/blob/b9d365435ad92094adde681d691b7a4ecd036194/README.md), [Agents SDK nel repo](https://github.com/kentcdodds/kody/blob/b9d365435ad92094adde681d691b7a4ecd036194/docs/contributing/cloudflare-agents-sdk.md), [`execute` e Workflows](https://github.com/kentcdodds/kody/blob/b9d365435ad92094adde681d691b7a4ecd036194/docs/use/execute.md).

Per un agente che deve **davvero** usare Docker dentro un ambiente isolato, esiste un riferimento più diretto: le [Docker Sandboxes ufficiali](https://docs.docker.com/ai/sandboxes/get-started/) eseguono l'agente in una microVM con daemon Docker privato, filesystem e rete propri; la [documentazione di sicurezza](https://docs.docker.com/ai/sandboxes/security/) distingue esplicitamente quel daemon da quello dell'host. Questa è una *candidata da prototipare*, non una prova che l'API sia già integrabile senza modifiche con Kestrel/Codex App Server. Va misurata su una macchina da 16 GB e su #142, inclusi cold start, memoria della VM, immagini, concorrenza e accesso all'endpoint LLM privato.

## Raccomandazione basata su #142

Usare una matrice di capacità prima della run: modello raggiungibile; workspace/OS; Docker daemon o servizi equivalenti; browser; memoria/CPU/PID; rete; comandi approvati. Per il profilo leggero usare sandbox container con budget calibrato. Per #142 scegliere un profilo Docker-capable **solo se esiste un worker reale** (microVM/daemon privato, o host fidato come esplicito compromesso); i check devono usare eseguibili portabili e la stessa workspace. Non rivedere tre volte il codice quando fallisce una capacità del runner e non trasformare quell'errore in una domanda di prodotto all'operatore. Il provider o plugin è il punto di aggancio, **non la capacità computazionale stessa**.

Questa è una proposta per Kestrel, inferita dalle fonti e dalla misurazione di #142, non una dichiarazione che Fabro garantisca test Docker annidati per qualsiasi repository.
