# Factory runner: esecuzione dell'agente, Docker e risorse

**Ricerca del 2026-10-01.** Domanda: dove e con quali risorse l'agente di implementazione lavora sul codice, avvia comandi e ambienti di progetto Node o Flutter, anche se usano Docker, senza esporre inutilmente l'host dell'operatore? La verifica formale è il confine successivo, richiamato solo dove serve a distinguere un ambiente utilizzabile da un risultato provato. Questa nota separa capacità documentate e proposte; non certifica alcun nuovo runner eseguito.

## Risultato

Il vincolo osservato in Kestrel è **una scelta del runner attuale, non un limite inevitabile delle software factory**. Il contratto corrente mette Codex `exec-server` in un container Linux usa-e-getta, senza rete né socket Docker host, e avvia ciascun comando di verifica in un nuovo container. Il checkout, il checkpoint Git e lo smontaggio certo restano sotto la custodia di Kestrel ([contratto di esecuzione](./factory-execution-runtime-contract.md), [ADR 0005](../adr/0005-own-sandbox-custody-with-the-agent-run.md)). Il checkout runtime `runtime/current`, più recente dell'`origin/master` su cui si basa questa nota, impone 2 GiB, 2 CPU e 128 PID al container ([configurazione runtime locale](/Users/silvioceccarini/Projects/kestrel-runtime/apps/web/src/codex-execution-runtime.ts:127)); questo protegge la macchina ma non soddisfa automaticamente un test che esegue `docker compose` o un processo Node più grande.

Sul Mac osservato `sysctl hw.memsize` restituisce 25.769.803.776 byte (24 GiB), mentre `docker info` restituisce 8.319.238.144 byte (circa 7,75 GiB) per la VM Linux di Docker Desktop. Sono tre budget diversi: RAM dell'host, RAM della VM Docker Desktop, limite del singolo container. Alzare solo il limite del container da 2 a 8 GiB non può creare RAM che la VM non possiede. Docker documenta il limite configurabile della VM (default circa metà RAM host) e consiglia di aumentarlo per carichi multi-container; documenta anche che un container senza limite può consumare memoria fino alla pressione sul sistema, con rischio di OOM per altri processi ([Desktop settings](https://docs.docker.com/desktop/settings-and-maintenance/settings/), [resource constraints](https://docs.docker.com/engine/containers/resource_constraints/)). Questi sono rilievi locali, non misure di picco del test #142.

Non esiste dunque una sandbox «senza limiti» in senso operativo. Si può rinunciare a un hard cap del singolo container (Docker lo permette), ma resta il budget fisico del Mac o del provider, e bisogna evitare che run concorrenti saturino l'host ([Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/)). Fabro espone il trade-off nella configurazione dell'ambiente; Docker Sandboxes offre un confine VM con Docker interno; Warp separa ambiente e runner shape. **Inferenza per Kestrel:** scegliere il profilo di esecuzione dell'agente *prima* della run può consentirgli di costruire, avviare e interrogare il progetto senza chiedere decisioni tecniche all'operatore a metà compito.

## Warp: ciò che è visibile del runner di implementazione

Warp separa **control plane** (coordinamento, configurazione, trace e inferenza) da **execution plane** (checkout, setup, strumenti, build e comandi), eseguito su host Warp o worker del cliente. Per le Factory, il runner definisce OS, architettura, immagine e shape vCPU/RAM; la definizione di Factory indica repo, setup e secret, mentre l'host decide dove gira. Il backend self-hosted può creare un container Docker per run, un Kubernetes Job per run oppure una workspace distinta direttamente sull'host; quest'ultima condivide OS e kernel. Queste sono capacità documentate, non dedotte dal linguaggio di implementazione ([Warp infrastructure](https://docs.warp.dev/factories/infrastructure-and-security/), [self-hosting](https://docs.warp.dev/platform/self-hosting)).

Le [environments Warp](https://docs.warp.dev/platform/environments/) dichiarano immagine, repository e comandi di setup per l'agente cloud; il runner sceglie hardware/OS separatamente. La [documentazione runner](https://docs.warp.dev/platform/runners/) dice che Linux hosted parte in container fresco e può avviare container Docker e VM basate su KVM, incluso l'emulatore Android; macOS hosted usa VM Apple Silicon con Xcode e simulatori. Il [worker pubblico `oz-agent-worker`](https://github.com/warpdotdev/oz-agent-worker) mostra come un processo Go riceve task via WebSocket e li instrada a Docker, Kubernetes, Direct o a un command dispatcher dell'operatore; nella variante Docker il socket sta nel worker fidato, e nella variante Direct il processo agente usa la RAM dell'host senza applicare le shape del container. Sono quindi backend alternativi dello **stesso modello di agente**, con confini e budget diversi. Non segue che il container Docker self-hosted permetta Compose *all'interno* del container agente: l'accesso del worker al daemon host serve prima di tutto a creare il container del task.

La [repository `warpdotdev/warp`](https://github.com/warpdotdev/warp) espone il client Rust (AGPL, framework UI MIT), compreso codice che gestisce comandi shell dell'agente nel client ([`shell_command.rs`](https://github.com/warpdotdev/warp/blob/master/app/src/ai/blocklist/action_model/execute/shell_command.rs)). Warp dichiara però che l'harness è diviso fra client Rust e server Go **non ancora aperto** ([intervento del fondatore](https://github.com/warpdotdev/warp/discussions/9619)); il [worker self-hosted](https://github.com/warpdotdev/oz-agent-worker) è un'altra repository pubblica Go. Pertanto non si può ricostruire interamente da `warpdotdev/warp` come il servizio proprietario ammetta capacità, gestisca ogni errore del processo o riprenda una sessione dopo crash. Le docs del worker mostrano comportamenti specifici di cleanup/recovery per backend, ma non provano che tutte le implementazioni di Factory conservino il medesimo workspace dopo un'interruzione ([worker README](https://github.com/warpdotdev/oz-agent-worker)).

La lezione trasferibile non è «riscrivere il runner in Rust»: compilatore Node, Gradle, browser, Docker e emulatori sono **processi figli** e consumano RAM/CPU/disk secondo il sistema che li ospita. Cambiare linguaggio del controller non rimuove il limite della VM o del cgroup ([Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/)). La separazione fra *workspace/toolchain*, *shape* e *backend di esecuzione* è invece il pattern concreto che permette a Warp di usare host, container o cloud secondo il progetto, con differenze dichiarate di fiducia e costo.

## Docker dentro Docker: opzioni reali

| Opzione | Cosa abilita | Costo principale | Valutazione per Kestrel |
| --- | --- | --- | --- |
| Socket Docker host nel container agente (`/var/run/docker.sock`) | Compose e Testcontainers con modifiche minime | Il processo agente controlla il daemon host e può montare il filesystem host; Testcontainers chiama questo pattern *Docker wormhole* ([Testcontainers](https://java.testcontainers.org/supported_docker_environment/continuous_integration/dind_patterns/), [Docker security](https://docs.docker.com/engine/security/)). | Da evitare per codice di repository non fidato. Inoltre rompe il confine no-socket del contratto attuale. |
| `docker:dind` in un container | Daemon separato dal daemon host | Il setup ordinario richiede privilegi aggiuntivi; anche DinD rootless sotto daemon rootful usa `--privileged`, e risorse/storage/rete si sommano ([Docker rootless DinD](https://docs.docker.com/engine/security/rootless/tips/), [Testcontainers](https://java.testcontainers.org/supported_docker_environment/continuous_integration/dind_patterns/)). | Non innestarlo nel container ristretto corrente. Una VM esterna rende molto più pulito il confine privilegiato. |
| Servizi sibling avviati dal controller | Database/browser o altri servizi noti sulla rete del task, senza socket nel codice agente; GitHub Actions usa service container per job ([GitHub](https://docs.github.com/en/actions/tutorials/use-containerized-services/use-docker-service-containers)). | Richiede manifest/policy e adattare test che invocano Compose in proprio; non copre qualsiasi progetto Docker arbitrario. | Buon percorso leggero per stack dichiarati, ma insufficiente come unica risposta alla domanda dell'utente. |
| MicroVM con daemon interno, locale o remota | Il progetto può usare Docker/Compose liberamente **dentro** un confine per-run; Docker Sandboxes lo documenta esplicitamente ([Docker](https://docs.docker.com/ai/sandboxes/security/isolation)). | Più memoria, disco, provisioning, integrazione con trasporto Codex e gestione dello stato; i cloud runner aggiungono costo e dipendenza di rete. | Candidato più promettente per test generici, da validare con prototipo sul vero path Kestrel prima di sceglierlo. |

Per Node, memoria del processo V8, eventuali worker, browser e servizi del test consumano il budget **insieme**: aumentare `--max-old-space-size` può evitare un limite V8, ma non aumenta la RAM della VM/container ([Node CLI](https://nodejs.org/download/release/v22.12.0/docs/api/cli.html), [Docker](https://docs.docker.com/engine/containers/resource_constraints/)). Per Flutter bisogna distinguere test Dart/Flutter headless da integrazione con dispositivo/emulatore, test desktop Linux con display virtuale e build iOS con Xcode su macOS ([Flutter integration tests](https://docs.flutter.dev/testing/integration-tests), [Flutter iOS](https://docs.flutter.dev/deployment/ios)). L'emulatore Android con accelerazione richiede un hypervisor e Google avverte che non può girare accelerato dentro un'altra VM come Docker ([Android emulator acceleration](https://developer.android.com/studio/run/emulator-acceleration)). **Inferenza:** neppure una microVM Linux con Docker interno è runner universale per ogni target Flutter; la capacità dichiarata deve includere OS, dispositivo, display e virtualizzazione, oltre a RAM e Docker.

## Alternative da valutare per Kestrel

Sono **quattro confini di esecuzione diversi**: host fidato, container ristretto con servizi esterni, VM locale privata e runner remoto. Account OS dedicato è un rafforzamento del primo, non isolamento equivalente a una VM; Docker-in-Docker è una variante tecnica del terzo solo quando il daemon vive nella VM, altrimenti richiede privilegi nel container esistente. La tabella separa capacità dalla decisione di prodotto. I riferimenti ufficiali sono [Fabro local/Docker/Daytona](https://github.com/fabro-sh/fabro/blob/main/docs/public/execution/environments.mdx#L363-L425), [Warp runner e backend](https://docs.warp.dev/factories/infrastructure-and-security/), [Docker Sandboxes](https://docs.docker.com/ai/sandboxes/security/isolation) e [sicurezza dei runner self-hosted](https://docs.github.com/en/actions/reference/security/secure-use). Le colonne Kestrel sono valutazioni architetturali, non risultati di test.

| Alternativa | Docker/Flutter e RAM effettiva | Confine di fiducia, concorrenza, costo | Workspace, recupero, ADR 0005 |
| --- | --- | --- | --- |
| **Host locale fidato**, eventualmente utente OS dedicato | Docker/Compose host senza modificare gli script; Node usa RAM host, Android emulator può usare hypervisor host. Flutter iOS richiede host macOS/toolchain appropriata. | Minimo setup e nessuna VM aggiuntiva, ma il codice del repository possiede le facoltà dell'utente che lo esegue e il daemon Docker host è potente; un account dedicato riduce l'accesso ai file solo se permessi, Docker e credenziali sono davvero separati. La concorrenza va limitata per RAM/CPU dell'intero Mac. | Può usare checkout dedicato, ma **cambia il confine di contenimento approvato**: ADR 0005 e contratto del runtime richiedono revisione esplicita prima di permettere all'agente comandi host. Recovery deve censire e terminare processi/container figli host. |
| **Container agente ristretto + servizi controller** | Va bene per DB, browser o dipendenze dichiarate; il controller avvia sibling e passa endpoint. Non esegue Compose arbitrario dal test se il test continua a chiamarlo. RAM = somma container test + servizi sotto la VM Docker Desktop (~7,75 GiB oggi), non solo cap test. Flutter headless possibile con toolchain; emulatore accelerato resta un altro profilo. | Conserva il no-socket nel codice agente. Avvio più leggero di VM per run; richiede manifest dei servizi, gestione rete/porte e budget aggregato. Concorrenza locale limitata dalla VM Desktop. | È compatibile **in principio** con la custodia Kestrel se la Sandbox possiede anche identità/stop dei servizi; ADR 0005 va esteso nei dettagli di lifecycle, non invertito. Il controller deve provare teardown di ogni sibling prima di rilasciare la run. |
| **VM/microVM privata locale con Docker interno**, `sbx` o equivalente | Compose arbitrario nella VM; RAM configurabile entro host e overhead VM, distinta dal limite Desktop attuale se il nuovo runtime non usa quella VM. Flutter headless plausibile; Android emulator accelerato dentro VM non promesso. | Mantiene host Docker fuori portata, ma comporta VM, cache/immagini separate, tempo di avvio e pressione RAM/disk; una VM pesante alla volta può essere l'unica scelta sostenibile sul Mac. | Potrebbe preservare l'intento dell'ADR 0005 come nuovo adapter Sandbox; serve provare trasporto `exec-server`, snapshot/checkpoint del medesimo workspace, identità VM e cleanup certo. Il CLI `sbx` locale non è ancora installato; nessuna fattibilità dimostrata. |
| **Agente su runner remoto effimero** (hosted o self-hosted) | Docker e capacità dipendono dal runner scelto; Warp offre Linux con Docker/KVM e macOS VM, con shape vCPU/RAM dichiarata. RAM locale non vincola i processi dell'agente remoto. | Più capacità e concorrenza espandibile, ma costo, coda, rete, credenziali e disponibilità. Un host self-hosted persistente non è automaticamente pulito; preferire istanza effimera per codice non fidato. | Il workspace/checkpoint dell'agente va trasferito o custodito sul runner con identità esatta; servono adapter remoto, cancellazione, riconciliazione e cleanup. L'ADR 0005 conserva l'obbligo di custodia, ma l'implementazione Docker locale corrente non basta ([Warp runner](https://docs.warp.dev/platform/runners/), [worker](https://github.com/warpdotdev/oz-agent-worker)). |

La scelta dipende dal contratto di fiducia del prodotto: se tutti i repository sono fidati e l'utente accetta esecuzione host, la prima via è la più semplice; se il codice può essere ostile, non usare l'host come soluzione automatica. Se i test richiedono solo servizi dichiarati, il controller con sibling evita il costo della VM privata. Se Compose arbitrario è requisito normale, VM privata locale o remota sono le due ipotesi da misurare. **Nessuna delle quattro è ancora validata sul percorso Codex/Kestrel.**

## Percorso di prova prima della scelta

1. Definire un **profilo di esecuzione dell'agente per progetto**: checkout/workspace, immagine/toolchain, necessità di Compose/servizi, rete, OS/architettura, memoria/CPU/PID/disk, eventuale emulatore/display e comandi di setup. Una preflight controlla la capacità *prima* di avviare l'agente; la run registra backend, risorse e identità del workspace. È la distinzione ambiente/runner già documentata da [Fabro](https://github.com/fabro-sh/fabro/blob/main/docs/public/execution/environments.mdx#L199-L201) e [Warp](https://docs.warp.dev/platform/runners/), adattata alla custodia Kestrel dell'[ADR 0005](../adr/0005-own-sandbox-custody-with-the-agent-run.md).
2. Mantenere il container ristretto come baseline e fare **due esperimenti comparabili**: (a) controller-managed service containers per gli attuali test Kestrel; (b) VM privata per gli stessi comandi Compose non modificati. Misurare tempo di setup, picco RAM/disk/CPU, numero massimo di run, rete e cleanup. In (b) Codex App Server e autenticazione possono restare sul controller, ma bisogna provare `exec-server`, checkout privato, daemon interno e teardown prima del checkpoint. È una proposta sperimentale, non compatibilità già dimostrata ([contratto Kestrel](./factory-execution-runtime-contract.md), [Docker Sandboxes](https://docs.docker.com/ai/sandboxes/security/isolation)).
3. Fare admission control sui budget aggregati delle run concorrenti, misurare picco RSS/CPU/PID/disk nei test reali e scegliere classi di risorse in base ai dati. Su questo Mac il collo di bottiglia iniziale del Docker Engine corrente è la VM ~7,75 GiB; `sbx` usa un runtime proprio e va misurato separatamente. Il `sbx` CLI non è installato qui, mentre `docker sandbox --help` dice che il vecchio comando è stato rimosso: niente affermazione di fattibilità locale senza installazione e prova. Le docs `sbx` richiedono macOS Sonoma+ e Apple silicon per uso locale; questo host è `arm64` ([installazione](https://docs.docker.com/ai/sandboxes/install/)).
4. Provare la ripresa dell'**agente di implementazione** dopo stop/crash su ciascun backend: il processo figli e i container avviati dal progetto devono avere identità e cleanup verificabili; il checkout cumulativo deve riaprire sul checkpoint corretto. Solo dopo, al confine downstream, i controlli di accettazione vanno eseguiti sulla revisione esatta e non possono risultare superati se omessi o falliti ([ADR 0005](../adr/0005-own-sandbox-custody-with-the-agent-run.md), [GitHub required checks come esempio di vincolo sulla revisione](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)).

### Prove ancora necessarie

- Installare `sbx` in un ambiente di prova e misurare creazione VM, memoria/disk a riposo e sotto `npm` + Compose/browser, capacità massima sul Mac da 24 GiB e concorrenza sostenibile. Non farlo nel runtime persistente senza percorso di cleanup e ownership.
- Provare che il Codex App Server host possa parlare con `exec-server` nella VM tramite un canale limitato, senza socket host né chiavi nel workspace; misurare continuità dopo restart, stop certo, checkpoint Git e policy di rete.
- Su un checkout esatto di #142, far lavorare l'agente con gli stessi comandi di sviluppo/setup e un `docker compose` del progetto, annotando fallimenti di capacità (`ENOENT docker`, OOM, saturazione worker) separatamente dai fallimenti di codice. Verificare se gli script Compose presuppongono path/mount del daemon host: un daemon privato cambia quei path. I test di accettazione restano una prova successiva.
- Provare almeno un progetto Flutter: test headless nel runner Linux e, separatamente, verifica Android/iOS su piattaforma idonea. Non assumere che Docker interno abiliti un emulatore accelerato.

**Raccomandazione per l'installazione locale osservata:** rendere il backend di esecuzione una capacità dichiarata per progetto e iniziare da un adapter **Direct per repository esplicitamente fidati**, su checkout di task posseduto da Kestrel, con strumenti locali e Docker Desktop del Mac. È la via più corta per provare Node, Compose e Flutter su macOS senza trasporto cloud o un'ulteriore VM; usa il budget RAM host per i processi host, ma i container Compose restano nel budget della VM Docker Desktop, oggi ~7,75 GiB, da dimensionare e misurare a parte. Imporre admission di run pesanti, registrare processi/container creati e provarne la terminazione e la ripresa; definire la fiducia *prima* dell'avvio del task, senza decisioni tecniche a metà esecuzione. L'adapter Direct **non è conforme all'attuale confine di isolamento**: prima di abilitarlo occorre cambiare esplicitamente ADR 0005 e contratto runtime, e non attivarlo per repository non fidati. Per questi mantenere il container ristretto oggi e provare una VM privata con Docker interno come secondo backend. Questo è un ordine di implementazione proposto, non un path già validato.

Cloudflare Containers è un candidato remoto Linux credibile quando servono disponibilità e capacità esterne al Mac; non è la prova che Kody già svolga questo lavoro. La shape pubblica da 12 GiB, la persistenza esplicita e l'integrazione con autenticazione Codex/`exec-server` rendono prematuro sceglierlo come primo backend Kestrel. Un controller con servizi sibling resta utile per progetti dichiarati, ma non esegue Compose arbitrario da un agente. Il limite di quota del modello e il timeout di run sono problemi ortogonali: più RAM o Docker non li eliminano.

Cloudflare pubblica anche un [tutorial per coding agent](https://developers.cloudflare.com/sandbox/get-started/build-a-coding-agent-runner/) e una [variante Codex](https://developers.cloudflare.com/sandbox/coding-agents/codex/): quindi la fattibilità *generica* di un coding agent su Cloudflare è documentata. La variante Codex usa CLI `codex exec` con AI Gateway e credenziali OpenAI API/billing nel gateway, non il percorso App Server con autenticazione Codex host adottato oggi da Kestrel. Il tutorial esegue una task e restituisce diff; non dimostra la ripresa del workspace e delle conversazioni Kestrel, né il caso Compose del suo progetto. Questa differenza di integrazione, non l'assenza di un prodotto Cloudflare, sostiene la priorità Direct locale.
