# Project board and planning chat

Selecting a Project opens its Kanban: To do, In progress, In review and Completed. Existing planning
conversations appear in To do; approved Work Items show their persisted execution state and
blockers. Opening a Work Item leads to its Feature board. The separate **Pull requests** action
opens the existing review inbox; Settings remains installation navigation.

**+ New** in To do and **Start plan** in the sidebar open a blank planning composer. Neither creates
a Feature or asks for a title. The first accepted prompt atomically creates the Feature, message,
retained Skill selection and queued turn. A rejected prompt leaves no abandoned conversation.

The composer URL includes an opaque request identity. Retrying an uncertain submission preserves the
original text and Skill selection. Reloading checks the authenticated Project request endpoint and
opens the accepted conversation when one exists. Unsent text stays in the mounted composer; it is
not saved in browser storage. Browser closure never cancels an accepted turn.

The first normal planning reply includes a short title generated by the selected runtime. **New
plan** remains the usable placeholder if the runtime cannot produce a valid reply. The Operator can
rename the conversation from its header; a pending naming turn cannot overwrite that choice. Titles
and replies are read consistently with the saved turn status. Naming does not change an approved
plan or grant implementation authority.

Public commands use the existing session, same-origin and CSRF checks:

- `POST /api/v1/projects/:projectId/planning` accepts a first prompt and returns the Feature,
  message and turn identities.
- `GET /api/v1/projects/:projectId/planning/:requestId` recovers that Operator's accepted request
  within the canonical Project, or returns no Feature.
- `POST /api/v1/projects/:projectId/features/:featureId/title` saves an idempotent explicit rename.

Reusing a mutation request with changed input is a conflict. Replaying a first prompt after a rename
returns the same immutable message and turn identities with the current Feature metadata.
